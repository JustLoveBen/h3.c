# H3.c RTX 5090 — 480P 5s ≤10s 插件路径极致优化计划

> **日期：** 2026-10-04 起。**机器：** 192.168.0.238，1×RTX 5090 32GB，sm_120。

| 其它 | 0.056s | 0.4% | | |

**关键发现（定刀口优先级）：**
1. **sol 的 pre/post aux（1.78s）竟然超过 sol SDPA 本体（1.73s）**——12232 个 reduce/fill/elementwise 小核是稀疏注意力的隐藏开销。**C1 刀口 = 压 sol aux（融合 reduce/fill、减 instance），理论可回收 ~1.5s。**
2. **DiT INT8 GEMM 3.59s 是最大单一本征**，压它只能靠更强 INT8 tensor-core 核（sm_120 原生）或降 FLOPs（已 turbo4 蒸馏到底）。
3. **quant/dequant + cast/prescale 合计 2.29s（16%）全是精度中转**——GEMM epilogue 融合（dequant 并进 GEMM 输出）可消大半，**C2 刀口，理论 ~1.5-2s**。
4. **SIMT sgemm 1.15s 是 F32 未走 tensor core 的浪费**，升 F16/INT8 可回收 ~0.8s，**C3 刀口**。
5. VAE GEMM 2.46s + VAE elementwise 0.43s ≈ 2.9s（与 vae_blocks 3.4s 对上，差为 launch 间隙）。

**结论：** sol 臂 GPU 总 14.37s 中，**可压缩的「非本征」开销（sol aux 1.78 + quant/cast 2.29 + SIMT 1.15 ≈ 5.2s）占 36%**。若 C1+C2+C3 全落地，DiT+VAE 可从 ~13.9s → ~8.7s，total 16.76s → ~11.5s。**要破 10s 还需 DiT INT8 GEMM 本征再压 ~2s（sm_120 原生 INT8 tensor core）。**

- 命名沿用既有约定：`H3_*` env 或 `--*` flag，且必须在 `--help`/文档登记。
- 每个插件开关附：开关名、默认值、效果、质量影响、实测秒数。

### 1.9 C2 复核：GEMM epilogue 融合（**已部分落地，余量重估**）

**重要修正（2026-10-04 续拍）：** `dit_fused_epi: on gemm_epi=1` 在基线 log 已开（R31 里程碑已做）。nsys 里残留的 quant/dequant/cast 2.29s **不是可全融的 epilogue**，而是：
- `dequant_i32_swiglu`(0.54s)/`dequant_i32_gate`(0.34s)/`dequant_i32_vec4`(0.34s)：FFN 两 GEMM **之间**的激活反量化+swiglu/gate，**无法融进单个 GEMM epilogue**（依赖第一个 GEMM 完整输出）。要消须把 swiglu/gate 融进 FFN-GEMM1 的 epilogue（部分可行）。
- `quantize_act_per_row_f16`(0.25s)：INT8 GEMM **前**的激活量化，须等上一层输出，**无法前移**。
- `f32_to_f16_row_prescale`(0.44s)+`f16_to_bf16`(0.19s)+`bf16_to_f32`(0.09s)：tensor 格式边界（sol 要 BF16_BTHD），**换 sol 输入格式可消**，但牵 sol 接口。

**C2 余量重估：** 真实可融空间 ~**0.9-1.2s**（FFN swiglu/gate 融进 GEMM1 epilogue），**不是 2.29s**。开关 `H3_DIT_FFN_EPI_FUSE`。难度中高（要写 F16 swiglu epilogue 核）。

**修正后路径预测：** 16.76s − C1(1.5) − C2(1.0) − C3(0.8) − C6/C7(1.5) − C8(0.4) ≈ **11.5s**。**要破 10s，C5（INT8 GEMM sm_120 原生，3.59s→~1.5s）从「加分项」变成「必需项」。**

**施工方向（全部 opt-in，不改 sol 数值语义）：**
- **C1a（低风险，~0.7s）：** sol `preprocess.py`/`interface.py` 中冗余 `zeros→empty`（kc/vc/threshold 全写则零填充无意义）。开关 `H3_SOL_AUX_EMPTY`。**注意：须逐 call 验证确实全写，masked/pad 区若靠零初始化则不可改**。
- **C1b（中风险，~0.5s）：** `_reduce_kc`+`_reduce_vc` 融合为单 triton 核双输出（k/v 同 grid/shape/stride）。开关 `H3_SOL_KV_FUSE`。

**红线：** sol 是稀疏注意力，改 aux **不能改数值输出**（checksum 必须逐 bit 一致），否则破坏质量地板。每步 A/B 对 checksum。

**关键实测修正（推翻 §1.5/§1.6 的 aux 归因）：**

1. **nsys 里的 aux 大头不在 DiT 窗口内。** 对 `kpia-sol-nsys/dit_nsys.sqlite` 按 stream-7 时间分桶：`_reduce_kc/vc` 的 3219/3528 个实例中**只有 199/199 个落在 DiT 窗口**（0.028s+0.027s），其余 ~6600 个与全部 5085 个 `FillFunctor`（0.70s）集中在两个时段：① ~2-4s 的 **sol QKVO warmup/init 段**（triton autotune 在每种 T 下 sweep 8 配置 ×2 核，每配置留 1 实例），② ~16-20s 的 **VAE 解码段**（fill 是 VAE 的 F32 canvas/scratch 零初始化，与 sol 无关）。DiT 稳态每层步的 sol aux 实际只有 kc+vc+diag+stats ≈ **0.43ms**（对照微基准），200 次合计 ~0.086s——**不是 §1.5 估的 1.78s**。
2. **C1b 融合正确但无收益。** 微基准（T=15477）：orig 两核 0.278ms vs 融合单核 0.278ms（GPU 时间 0.275→0.275ms）——reduce 每核读 227MB 已打满 ~1.6TB/s 显存带宽，融合省不掉数据量。唯一收益是 launch 数减半（200 次 fwd 省 200 次 launch ≈ 几 ms），淹没在 run-to-run 噪声里（ctrl-a vs ctrl-b dit 差 +17.5ms、total 差 +470ms 主要是 VAE/ppm 段噪声，非 C1b 引起）。
3. **更快的 reduce 变体与 bit 红线冲突。** mega-block（一个 CTA 归约多个 64-token block）指针加载版可快 ~5×（0.048ms vs 0.278ms），但 tl.sum 归约顺序随 tile 形状/num_warps 改变，**无法与官方核逐 bit 一致**（即使官方核自身在 num_warps=4↔8 间也变 bits）。按数值同一性红线放弃。
4. **FillFunctor 5085×0.70s 不可动**：绝大部分在 VAE 段（F32 canvas 零初始化，改 empty 会破坏 VAE 数值），与 sol 无关。

**C1 结论：** sol aux 在 480p DiT 稳态的真实权重只有 ~0.09s/clip（0.5% dit），**不是通往 10s 的刀口**。C1b 已按插件规则落地（`H3_SOL_KV_FUSE`，默认 OFF，bit-identical，可留作无害选项）；§1.5 的「sol aux 1.78s 超 SDPA 本体」应修正为「sol SDPA 本体 1.73s + DiT 内 aux 0.09s + warmup/autotune 一次性 ~1.05s + VAE fill 0.70s」。后续刀口应转向 C2（epilogue 融合 quant/dequant/cast 2.29s，DiT 窗口内真实存在）与 C5（INT8 GEMM 本征 3.59s）。成片 `kpia-sol-c1aux/ctrl-a/run_r{1,2}.mp4`、`ctrl-b/run_r{1,2}.mp4` 待人工确认。

### 1.7 C3 施工卡：SIMT sgemm → TF32/F16 tensor core（nsys 1.15s）

**定位：** `h3_cuda_gemm_f32_dd`（`h3_gpu_cuda.cu:2198`）走纯 `cublasSgemm`（SIMT F32，无 tensor core）。调用方：
- **VAE GEMM**（`h3_vae_int8_cuda.c:787/952/1000/1039/2664`：qkv/out/w1/w2/embed）→ 对应 nsys `simt_sgemm_256x128`(0.74s,860×)+`64x128`(0.37s,800×)。
- **DiT LoRA**（`h3_dit_w4a8.c:819/825`：`d_lora_A/B`）与部分 DiT F32 GEMM（`:3792/4068/5855`）。

**已有 tensor-core 旁路：** `h3_cuda_gemm_f32_dd_tf32_ex`（`:2245`）用 `CUBLAS_COMPUTE_32F_FAST_TF32`+`DEFAULT_TENSOR_OP`，失败自动回退 SIMT。DiT LoRA 主路（`:804/811`）**已用 TF32**。

**数值红线（与 C1 不同）：** TF32 是 10-bit mantissa，**非 bit-identical**。所以 C3 不能像 C1 那样要求 checksum 逐位一致——它是**精度档开关**，验收标准是 waffle/视觉 A/B 在质量地板内 + latent checksum 漂移有界（记录漂移量，不要求 0）。
- **C3 开关：** `H3_VAE_GEMM_TF32=1`（VAE 四 GEMM 走 `_tf32_ex`）、`H3_DIT_GEMM_TF32=1`（DiT F32 GEMM）。默认 OFF 保持 bit-identical F32。
- **预期：** VAE SIMT 1.11s → TF32 ~0.3s（−0.8s）；DiT 部分另计。
- **风险：** TF32 在 VAE decoder 可能引入轻微色偏——必须 waffle + 抽帧人工对照，超地板则退回 F32 默认。

### 1.8 C5 施工卡：DiT INT8 GEMM sm_120 本征（破 10s 关键，nsys 3.59s）

**定位：** DiT INT8 GEMM 主力是 `cutlass_80_tensorop_i16832gemm_s8_128x128_64x6`（3.585s, 3200 inst, sm_**80** 核）。**这是 Ampere 代 INT8 tensor-core 核，不是 Blackwell sm_120 原生**。

**关键事实（2026-10-04 续拍查证）：** DiT INT8 GEMM 走 **cublasLtMatmul + IMMA（INT8 tensor core）**（`h3_gpu_cuda.cu:2481` `cublasLtMatmulAlgoGetHeuristic`）。nsys 里的 `cutlass_80_i16832` 是 **cublasLt 启发式为该 M/N/K 在 sm_120 上选出的最优核**——即 cublasLt 库内**没有更快的 sm_120 原生 INT8 核**适配此形状。
- **含义：** C5 不是「换个 flag 就提速」，而是**手写 sm_120 cute/cutlass INT8 GEMM 核超过 cublasLt**——工作量最大、收益不确定（cublasLt 已调优）。
- **机会窗口（若做）：** ① cublasLt 工作区/启发式可能次优，可强制遍历全部 heuristic 选最快（低风险先试）；② INT8 GEMM 的 K 维若可增大（合并 QKV）则 tensor-core 利用率升；③ sm_120 的 INT8 每 clock 吞吐与 sm_80 核的差距。
- **先做 C5a（低成本）：** 遍历 cublasLt 全部 heuristic（不只第一个 fit workspace 的），选实测最快——可能白捡 5-15% INT8 GEMM。开关 `H3_DIT_INT8_ALGO_BEST`。
- **判定：** C5a 先试；C5 全量（手写 sm_120 核）是破 10s 的最后一搏，排在所有其它刀口之后。

**C5a 实测（2026-10-04，`kpia-int8-autotune`，sol 臂 480p，`H3_DIT_INT8_ALGO_BEST=1`，repeat=2 ×2 次）：** 已落地于 `h3_gpu_cuda.cu`（默认 OFF 时字节级不变；ON 时每个 (m,n,k) slot 对全部 fit-workspace 候选跑 3 warmup + 5 timed 取 median，缓存进 `lt_i8[slot].heur`，每形状一次性）。
- **候选数：每个形状 cublasLt 只回 1 个 heuristic（algos=1）**——8 个形状（m∈{3200,4096} × n/k 四组合）全部 `best=#0 t == first-fit`，**best-vs-firstfit Δ = 0.000ms**。
- **结论：cublasLt 在 sm_120/CUDA13 上对这些 INT8 形状只暴露单一最优核，autotune 无候选可挑，0 收益。** 白捡 5-15% 的假设不成立（库内确无更快核）。
- hot clip2：baseline（`kpia-sol-480p`）dit=10367.3 total=16756.9 → C5a run1 dit=10376.9 total=16813.0、run2 dit=10382.5 total=16924.3（+0.1%/+0.3-1.0%，run-to-run 噪声内，非回退）。
- **latent checksum 逐位一致：** clip1=0xce0b5df2bcdb4ad3、clip2=0x5fc00e592bac60a4 与 baseline 完全相同（ctrl-off 与 autotune 两臂均一致）→ bit-identical 验证通过。
- sol 400/400 fallback=0；waffle 正常（clip2 frame b16 1.0-3.6 区间与 baseline 同档）；av_sync PASS（drift 8ms）。稳定性：repeat=2 连跑 2 次均 exit=0。
- 附带修正：autotune 计时前加 `(void)cudaGetLastError()` 清黏滞错误（远程树曾因此 VAE head 静默失败；本地树默认路径无 autotune，不受影响）。

## 1.10 Plugin 架构（2026-10-04）

**动机：** 开发期积累的实验性 `H3_*` 环境变量开关散落在 `h3_gpu_cuda.cu`、`h3_vae_int8_cuda.c`、`tools/h3_cuda_generate.c`、sol `preprocess.py` 四个文件中，以 ad-hoc `getenv()` 读取，缺乏统一编目与状态管理，存在代码腐化风险。本次重构为**模块化"插件"风格**：新技术方案通过统一接口引入，**不改变整体结构、不改变既有行为**。

### 1.10.1 注册表：`tools/h3_plugin.h`（单头文件，C/C++ 兼容，header-only）

每个插件 = `{ name(=env var), stage, description, default_on, precision_tier, status, since }`：

- **stage**（枚举）：`DIT / VAE / MUX / SOL / TE / AUDIO / GUARD / MISC`
- **precision_tier**：`bit-identical`（开启后仍逐位一致）/ `tf32` / `fp8` / `quality-tier`（如画质档 x264 preset）/ `n/a`（调试/profiling，无数值影响）
- **status**：`stable` / `experimental` / `dead-end-verified`（已验证死路，仅存档，防止重复踩坑）
- **since**：引入日期 YYYY-MM-DD

**API：**

| 接口 | 作用 |
| --- | --- |
| `h3_plugin_register(name, stage, desc, default_on, tier, status, since)` | 注册插件；重复注册更新元数据（保留缓存状态） |
| `h3_plugin_enabled(name)` | 返回开关当前是否生效（env 设置优先于默认；`""`/`"0"`=关，其余=开），结果按名缓存；未知名首次调用自动注册为 `experimental/MISC`，**保证迁移前即可工作** |
| `h3_plugin_list(buf, cap)` | 输出完整目录（按名称排序，稳定可 diff），供 `--list-plugins` CLI 使用 |
| `h3_plugin_report_startup()` | `H3_PLUGIN_REPORT=1` 时向 stderr 打印全部已注册插件及 on/off 状态（启动早期调用一次） |
| `h3_plugin_register_builtins()` | 幂等地预注册 `H3_PLUGIN_BUILTIN_DEFS` 全目录，使 `H3_PLUGIN_REPORT=1` 在任何调用点迁移前即可 dump 完整存量目录 |
| `h3_plugin_report(FILE*)` | 向给定流打印目录表（main() 在 `H3_PLUGIN_REPORT` 设置时调用） |
| `h3_plugin_count()` | 已注册插件数量 |

**CLI 集成：** `main()` 入口首先调用 `h3_plugin_register_builtins()`，随后若 `getenv("H3_PLUGIN_REPORT")` 非空则 `h3_plugin_report(stderr)` dump 全表；默认路径（无 env）除一次纯内存注册外零行为变化。当前目录共 **112 个插件**（含 sol preprocess.py 侧的 `H3_SOL_KV_FUSE` 与新增 GUARD 组）。

### 1.10.3 迁移状态与并行施工约束

- **调用点迁移（0 处，刻意跳过）：** 所有 `getenv`/`env_is_one` 读取处一行未动。注册表不依赖迁移即可工作——`h3_plugin_register_builtins()` 静态收录全部存量开关，报告功能完整可用；开关首次经 `h3_plugin_enabled()` 查询时亦会自动注册。后续拍可在无在飞编辑窗口期逐步迁移读取处。
- **不格式化/不移动** `h3_gpu_cuda.cu` / `h3_vae_int8_cuda.c` 的任何既有代码块；对既有文件的唯一编辑是 `tools/h3_cuda_generate.c`：`#include "h3_plugin.h"`（`__has_include` 守卫）+ main() 入口的 register/report 钩子 + waffle guard 的 `h3_plugin_register` 元数据登记（guard 逻辑本身为上一拍既有功能）。

### 1.10.4 新增插件规则（一行注册 + 验收门槛）

1. **一行注册**：`h3_plugin_register("H3_XXX", H3_PLUGIN_STAGE_DIT, "what it does", 0, H3_PLUGIN_PREC_BIT_IDENTICAL, H3_PLUGIN_STATUS_EXPERIMENTAL, "YYYY-MM-DD");`（或在 `H3_PLUGIN_BUILTIN_DEFS` 追加一行 `X(...)`）
2. **读取处**用 `if (h3_plugin_enabled("H3_XXX"))` 替代 `getenv` 判断。
3. **验收门槛（硬约束）**：
   - 默认 **OFF**；默认路径 bit-identical checksum 不变：**480p clip1=`0x28e8a880d52e9be1` clip2=`0xce0b5df2bcdb4ad3`**
   - waffle **1.0–1.7**（clip2 金线区间）
   - av_sync **PASS**
   - sol **400/400**（fallback=0）
   - TF32/fp8 类精度档插件豁免 bit-identical，但须 waffle + 视觉 A/B 在质量地板内并记录 latent 漂移量（§1.7 C3 先例）。
